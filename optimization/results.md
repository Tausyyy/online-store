# Роль 4 — Оптимизация запросов

Выбраны два бизнес-запроса из роли 2 (файл `queries/business_queries.sql`):

- **Запрос 1** — история заказов покупателя (`customer_id = 15`);
- **Запрос 2** — топ-10 самых продаваемых товаров среди доставленных заказов.

Оптимизация разная, чтобы показать два основных приёма: **индекс** (запрос 1) и
**переписывание запроса** (запрос 2). Тексты запросов лежат в
`optimization/q1.sql` и `optimization/q2_before.sql` (точные копии запросов
роли 2) и `optimization/q2_after.sql` (переписанный вариант).

## Условия измерений

| Параметр           | Значение                                                                                                                                                          |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| СУБД               | PostgreSQL 18 (Docker-образ `postgres:18`), настройки по умолчанию                                                                                                |
| Данные             | `generate_data.sql`, `tag=big`, `seed=42`, `order_items_count=3000000`                                                                                            |
| Объём              | customers 30 000, products 3 000, sku 15 000, orders 300 000, order_items 3 000 000                                                                               |
| Заказы по статусам | delivered 135 000, paid 36 000, created 30 000, in_assembly 24 000, awaiting_payment 24 000, handed_to_delivery 21 000, cancelled 15 000, return_processed 15 000 |
| Перед замерами     | `VACUUM ANALYZE`                                                                                                                                                  |
| Замер              | 1 прогревочный запуск + 5 замеров `EXPLAIN (ANALYZE)`, берётся **медиана**                                                                                        |

Абсолютные числа на другом компьютере будут другими. Сравнивать нужно «до» и
«после» на одной машине.

## Таблица измерений

| Запрос                                   | Что изменили           | До, мс | После, мс |   Ускорение |
| ---------------------------------------- | ---------------------- | -----: | --------: | ----------: |
| Q1: история заказов (`customer_id = 15`) | индексы (миграция 002) |  138,0 |       6,5 | в 21,2 раза |
| Q2: топ-10 товаров                       | переписан запрос       |  403,0 |     269,4 |  в 1,5 раза |
| Контроль: Q2 старый, но с индексами      | только индексы         |  403,0 |     397,9 |   в 1,0 раз |

Контрольная строка нужна, чтобы доказать: улучшение Q2 даёт именно
переписывание, а не индексы (1,0 раз — это в пределах погрешности).

Планы лежат в `optimization/plans/`: `q1_before.txt`, `q1_after.txt`,
`q2_before.txt`, `q2_after.txt`. Каждый план сохраняется **одним** запуском
сразу после `VACUUM ANALYZE`, поэтому в нём есть `read=...` (часть страниц
читалась с диска), а время `Execution Time` отличается от медианы (Q1: 134,7 →
9,0 мс, Q2: 405,3 → 262,1 мс). Одиночный запуск всегда колеблется, поэтому в
таблице стоит медиана.

В планах PostgreSQL 18 есть строки `Index Searches: ...` и числа вида
`rows=2350.00`. Это особенность формата этой версии, на смысл плана они не
влияют.

## Запрос 1 — индексы по внешним ключам

**Что было (план до).**

```
Parallel Seq Scan on order_items oi   ... rows=1000000 loops=3
Parallel Seq Scan on orders o         ... Filter: (customer_id = 15)
                                          Rows Removed by Filter: 99922
Buffers: shared hit=21407 read=14815
```

У `orders.customer_id` и `order_items.order_id` нет индексов: PostgreSQL создаёт
их сам только для `PRIMARY KEY` и `UNIQUE`, а для `FOREIGN KEY` — нет. Чтобы
найти 235 заказов покупателя, база вынуждена прочитать **все 300 000 заказов**
(каждый из трёх процессов отбрасывает по 99 922 лишние строки). Чтобы найти их
позиции, она читает **все 3 000 000 позиций**. Всего прочитано 36 222 страницы
(около 283 МБ) ради 2 350 строк результата.

**Что сделали.** Миграция `002_add_indexes`:

```sql
CREATE INDEX idx_orders_customer_id ON orders (customer_id);
CREATE INDEX idx_order_items_order_id ON order_items (order_id);
```

**Что стало (план после).**

```
Bitmap Index Scan on idx_orders_customer_id     ... rows=235
Index Scan using idx_order_items_order_id       ... rows=10 loops=235
Buffers: shared hit=1088 read=368
```

Теперь база по индексу сразу находит 235 заказов покупателя, а затем для каждого
заказа по второму индексу находит его позиции (по 10 штук). Читается 1 456
страниц (около 11 МБ) вместо 36 222, то есть примерно в 25 раз меньше. Полные
сканы таблиц `orders` и `order_items` исчезли, а вместе с ними и параллельные
процессы (`Gather`): для такого маленького объёма они не нужны. Таблицы `sku`
(15 000 строк) и `products` (3 000 строк) по-прежнему читаются целиком, но они
маленькие (232 и 44 страницы).

## Запрос 2 — сначала агрегация, потом соединения

**Что было (план до).** Каждый из трёх процессов делает следующее, время
накопленное:

| Шаг                                            |     Строк | Накопленное время |
| ---------------------------------------------- | --------: | ----------------: |
| чтение `order_items`                           | 1 000 000 |             57 мс |
| соединение с доставленными заказами (`orders`) |   450 000 |            194 мс |
| соединение с `sku`                             |   450 000 |            266 мс |
| соединение с `products`                        |   450 000 |            336 мс |
| группировка по `product_id`                    |     2 100 |            396 мс |

Исходный запрос сначала **соединяет** позиции с `sku` и `products`, и только
потом **группирует**. Два соединения подряд обрабатывают по 450 000 строк на
процесс (1,35 млн всего), хотя в итоге нужно всего 2 100 товаров, из которых
берутся 10.

**Что сделали.** Файл `optimization/q2_after.sql`: сначала группировка по
`sku_id` (прямо после соединения с доставленными заказами), потом соединения.

```sql
FROM (
    SELECT oi.sku_id, SUM(oi.quantity) AS sold
    FROM order_items oi
    JOIN orders o ON oi.order_id = o.order_id
    WHERE o.status = 'delivered'
    GROUP BY oi.sku_id
) AS t
JOIN sku s ON s.sku_id = t.sku_id
JOIN products p ON p.product_id = s.product_id
GROUP BY p.product_id, p.name
```

**Что стало (план после).** Те же 450 000 строк на процесс сворачиваются до 5
940 (по числу SKU с доставленными продажами) сразу после соединения с `orders`:
`Partial HashAggregate` заканчивается на 244 мс, затем `Gather` и
`Finalize HashAggregate` (около 254 мс). Соединения с `sku` и `products`
работают уже с 5 940 строк и занимают несколько миллисекунд вместо 142 мс. Время
одного запуска по плану упало с 405 до 262 мс.

**Почему выигрыш скромный (в 1,5 раза).** Основная работа осталась: нужно
прочитать все 3 млн позиций и соединить их с 135 000 доставленных заказов (около
183 мс из 262 мс в плане после). Эту часть переписывание не убирает, оно только
избавляет от двух лишних соединений над 1,35 млн строк. Количество прочитанных
страниц почти не изменилось (29 862 до и 29 018 после, около 230 МБ). Индекс тут
не помогает, потому что нужны **все** доставленные позиции (контрольная строка:
403 → 398 мс). Заметно ускорить такой запрос можно только уменьшением объёма
данных, например отдельной таблицей с готовой сводкой продаж, но это выходит за
рамки задания.

Это нормальный результат: не каждая оптимизация даёт десятикратный выигрыш, а
выбор приёма зависит от запроса. Для Q1 помог индекс, потому что запрос выбирает
**малую часть** таблицы; для Q2 индекс бесполезен, потому что запрос читает
**большую часть** данных.

Результаты старого и нового запроса 2 совпадают по значениям `total_sold`.
Скрипт сверяет их автоматически (шаг 5); сравнивается только `total_sold`,
потому что товары с равными продажами могут идти в другом порядке.

## Как воспроизвести

Через Docker (все шаги выполняются сами):

```bash
bash run_big.sh
```

Или вручную на своём PostgreSQL, в Git Bash (скрипт написан на bash):

```bash
export PGCLIENTENCODING=UTF8
export PGPASSWORD="пароль"
export DATABASE_URL="postgresql://postgres:пароль@localhost:5432/online_store_bench"

# 1. схема и миграция 001
psql "$DATABASE_URL" -f migrations/create_tables.sql.sql
psql "$DATABASE_URL" -f migrations/001_add_constraints.up.sql

# 2. данные: 3 000 000 строк в order_items
psql "$DATABASE_URL" -v tag=big -v seed=42 -v order_items_count=3000000 \
     -f scripts/data_generator/generate_data.sql

# 3. замеры до и после (сам применит и откатит миграцию 002)
./optimization/run_benchmark.sh
```

`PGCLIENTENCODING=UTF8` нужна на Windows, иначе русский текст в SQL-файлах
вызывает ошибку кодировки.

Скрипт сам откатывает `002`, если она уже применена, поэтому его можно запускать
повторно. Вернуть базу в состояние «до» вручную: `./scripts/migrate.sh down`.

Запрос 1 берёт `customer_id = 15`. Из-за неравномерной генерации у этого
покупателя много заказов (235 из 300 000). Для покупателя с меньшим числом
заказов время «после» будет ещё меньше, а «до» не изменится: без индексов запрос
в любом случае читает таблицы целиком.
