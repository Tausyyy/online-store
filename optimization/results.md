# Роль 4 — Оптимизация запросов

Выбраны два бизнес-запроса из роли 2:

- Запрос 1 — история заказов покупателя (`customer_id = 15`);
- Запрос 2 — топ-10 самых продаваемых товаров.

Оптимизация разная, чтобы показать два основных приёма: индекс (запрос 1) и переписывание запроса
(запрос 2).

## Условия измерений

| Параметр       | Значение                                                                            |
| -------------- | ----------------------------------------------------------------------------------- |
| СУБД           | PostgreSQL 18.3 (Windows), настройки по умолчанию                                   |
| Машина         | 8 ядер, 16 ГБ RAM                                                                   |
| Данные         | `generate_data.sql`, `tag=big`, `seed=42`, `order_items_count=3000000`              |
| Объём          | customers 30 000, products 3 000, sku 15 000, orders 300 000, order_items 3 000 000 |
| Перед замерами | `VACUUM ANALYZE`                                                                    |
| Замер          | 1 прогревочный запуск + 5 замеров `EXPLAIN (ANALYZE)`, берётся медиана              |

Абсолютные числа на другом компьютере будут другими. Сравнивать нужно «до» и «после» на одной
машине.

## Таблица измерений

| Запрос                                   | Что изменили           | До, мс | После, мс |   Ускорение |
| ---------------------------------------- | ---------------------- | -----: | --------: | ----------: |
| Q1: история заказов (`customer_id = 15`) | индексы (миграция 002) |  168,3 |       8,3 | в 20,3 раза |
| Q2: топ-10 товаров                       | переписан запрос       |  753,5 |     312,7 |  в 2,4 раза |
| Контроль: Q2 старый, но с индексами      | только индексы         |  753,5 |     702,7 |  в 1,1 раза |

Контрольная строка нужна, чтобы доказать: ускорение Q2 даёт именно переписывание, а не индексы.

Планы лежат в `optimization/plans/`: `q1_before.txt`, `q1_after.txt`, `q2_before.txt`,
`q2_after.txt`. Каждый план сохраняется одним запуском сразу после `VACUUM ANALYZE`, поэтому в нём
есть `read=...` (часть страниц читалась с диска), а время `Execution Time` немного отличается от
медианы (например, Q2 до: 629 мс в плане и 753 мс в медиане). Одиночный запуск всегда колеблется,
поэтому в таблице стоит медиана.

В планах PostgreSQL 18 есть строки `Index Searches: ...` и числа вида `rows=1961.00`. Это
особенность формата этой версии, на смысл плана они не влияют.

## Запрос 1 — индексы по внешним ключам

Что было (план до).

```
Parallel Seq Scan on order_items oi   ... rows=1000000 loops=3
Parallel Seq Scan on orders o         ... Filter: (customer_id = 15)
                                          Rows Removed by Filter: 99932
Buffers: shared hit=26532 read=14481
```

У `orders.customer_id` и `order_items.order_id` нет индексов: PostgreSQL создаёт их сам только для
`PRIMARY KEY` и `UNIQUE`, а для `FOREIGN KEY` — нет. Чтобы найти 204 заказа покупателя, база
вынуждена прочитать все 300 000 заказов (на каждом из трёх процессов отброшено по 99 932 лишние
строки). Чтобы найти их позиции, она читает все 3 000 000 позиций. Всего прочитано 41 013 страниц
(около 320 МБ) ради 1 961 строки результата.

Что сделали. Миграция `002_add_indexes`:

```sql
CREATE INDEX idx_orders_customer_id ON orders (customer_id);
CREATE INDEX idx_order_items_order_id ON order_items (order_id);
```

Что стало (план после).

```
Bitmap Index Scan on idx_orders_customer_id     ... rows=204
Index Scan using idx_order_items_order_id       ... rows=9.61 loops=204
Buffers: shared hit=818 read=430
```

Теперь база по индексу сразу находит 204 заказа покупателя, а затем для каждого заказа по второму
индексу находит его позиции (в среднем около 10 штук). Читается 1 248 страниц (около 10 МБ) вместо
41 013. Полные сканы таблиц `orders` и `order_items` исчезли, а вместе с ними и параллельные
процессы (`Gather`): для такого маленького объёма они не нужны.

## Запрос 2 — сначала агрегация, потом соединения

Что было (план до).

```
Partial HashAggregate (Group Key: p.name)        rows=3000, обработано 1000000 на процесс
  -> Hash Join с products                        rows=1000000
     -> Hash Join с sku                          rows=1000000
        -> Parallel Seq Scan on order_items      rows=1000000
```

Исходный запрос сначала соединяет 3 млн позиций с `sku` и `products`, и только потом группирует.
Каждый из трёх процессов проводит через оба соединения по миллиону строк, хотя в итоге нужно всего 3
000 строк (по числу товаров), из которых берутся 10.

По времени внутри одного процесса это выглядит так (по плану до):

| Шаг                       | Накопленное время |
| ------------------------- | ----------------: |
| чтение `order_items`      |             49 мс |
| + соединение с `sku`      |            273 мс |
| + соединение с `products` |            428 мс |
| + группировка по названию |            593 мс |

Что сделали. Файл `optimization/q2_after.sql`: сначала группировка по `sku_id` прямо в
`order_items`, потом соединения.

```sql
FROM (
    SELECT sku_id, SUM(quantity) AS sold
    FROM order_items
    GROUP BY sku_id
) AS t
JOIN sku s ON s.sku_id = t.sku_id
JOIN products p ON p.product_id = s.product_id
GROUP BY p.name
```

Что стало (план после).

```
Partial HashAggregate (Group Key: order_items.sku_id)   rows=15000 на процесс
  -> Parallel Seq Scan on order_items                   rows=1000000
Hash Join с sku       rows=15000
Hash Join с products  rows=15000
```

Три миллиона строк превращаются в 15 000 (по числу SKU) до соединений. В одном процессе: чтение
таблицы 48 мс, группировка по `sku_id` ещё около 165 мс (накопленно 213 мс). Оба `Hash Join`
работают уже с 15 000 строк, поэтому занимают несколько миллисекунд вместо 380 мс.

**Что не изменилось.** `Parallel Seq Scan on order_items` остался, и прочитано примерно столько же
страниц (около 25 000, то есть около 200 МБ). Чтобы посчитать продажи по всем товарам, нужно
прочитать все позиции заказов, и индекс тут не поможет. Это подтверждает контрольная строка: со
старым запросом и индексами время почти не изменилось (753 → 703 мс, разница в пределах
погрешности).

Результат старого и нового запроса одинаковый. Скрипт сверяет их автоматически (шаг 5).

## Как воспроизвести

В Git Bash (скрипт написан на bash):

```bash
export PGCLIENTENCODING=UTF8
export PGPASSWORD="пароль"
export DATABASE_URL="postgresql://postgres:пароль@localhost:5432/online_store_bench"

# 1. схема и миграция 001
psql "$DATABASE_URL" -f migrations/create_tables.sql.sql
psql "$DATABASE_URL" -f migrations/001_add_constraints.up.sql

# 2. данные: 3 000 000 строк в order_items
psql "$DATABASE_URL" -v tag=big -v seed=42 -v order_items_count=3000000 \
     -f scripts/data_generator/generate_data.sql

# 3. замеры до и после (сам применит и откатит миграцию 002)
./optimization/run_benchmark.sh
```

`PGCLIENTENCODING=UTF8` нужна на Windows, иначе русский текст в SQL-файлах вызывает ошибку
кодировки.

Скрипт сам откатывает `002`, если она уже применена, поэтому его можно запускать повторно. Вернуть
базу в состояние «до» вручную: `./scripts/migrate.sh down`.

Запрос 1 берёт `customer_id = 15`. Из-за неравномерной генерации у этого покупателя много заказов
(204 из 300 000). Для покупателя с меньшим числом заказов время «после» будет ещё меньше, а «до» не
изменится: без индексов запрос в любом случае читает таблицы целиком.
