# Участник 4 — MongoDB: CRUD и валидация

Каталог содержит реализацию CRUD-операций, JSON Schema Validation и проверку бизнес-правил для
документной части интернет-магазина одежды.

## 1. Граница ответственности PostgreSQL и MongoDB

Существующая PostgreSQL-модель не изменяется. В рамках этой реализации принято следующее разделение:

| Данные                                                         | Где хранятся                                                | Источник истины                                                                                       |
| -------------------------------------------------------------- | ----------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| Покупатели, учётные данные и роли                              | PostgreSQL (`customers`)                                    | PostgreSQL                                                                                            |
| Категории, товары, SKU, цены и остатки                         | PostgreSQL (`categories`, `products`, `sku`)                | PostgreSQL                                                                                            |
| Корзины, заказы, позиции заказов и платежные данные            | PostgreSQL (`carts`, `cart_items`, `orders`, `order_items`) | PostgreSQL                                                                                            |
| Гибкое описание карточки товара: характеристики, теги, галерея | MongoDB (`product_content`)                                 | MongoDB для контента карточки; `products` в PostgreSQL остаётся источником истины для базового товара |
| Отзывы покупателей                                             | MongoDB (`product_reviews`)                                 | MongoDB                                                                                               |
| Вопросы покупателей о товарах и ответы                         | MongoDB (`product_questions`)                               | MongoDB                                                                                               |

MongoDB не хранит копии паролей, цен, остатков, заказов и платёжных сведений. Это предотвращает
конкурирующие источники истины. Поля `productId` и `customerId` — ссылки на соответствующие
`BIGINT`-идентификаторы PostgreSQL, записанные в MongoDB строками. Строковое представление не теряет
точность больших `BIGINT` при передаче через JavaScript.

> Важно для интеграции: MongoDB не обеспечивает внешний ключ на PostgreSQL. Существование
> `productId` и `customerId` должно проверяться сервисным слоем при создании контента, отзыва или
> вопроса. В демонстрационном CRUD используются синтетические ID, поэтому примеры автономны и не
> изменяют PostgreSQL.

## 2. Коллекции и связи

### `product_content`

Один документ на товар. Содержит `productId`, заголовок, описание, динамический объект `attributes`,
массив `tags` и массив `gallery`. Характеристики и изображения встроены в документ, потому что
обычно читаются вместе с карточкой товара и редактируются как её часть.

### `product_reviews`

Отзыв содержит ссылки `productId` и `customerId`, оценку, текст, статус и даты. Коллекция реализует
связь «товар — отзывы» (1:N). Совокупность отзывов связывает покупателей и товары (M:N): один
покупатель может оставить отзывы о разных товарах, а один товар может иметь отзывы от разных
покупателей. Уникальный составной индекс `{ productId, customerId }` ограничивает число отзывов
одного покупателя на один товар одним документом.

### `product_questions`

Вопрос содержит ссылки на товар и покупателя, текст, необязательный ответ и статус. У товара может
быть много вопросов (1:N). Ответ хранится в том же документе, потому что относится только к
конкретному вопросу и обычно читается вместе с ним.

## 3. JSON Schema Validation

`validation.js` создаёт коллекции или обновляет валидаторы уже существующих коллекций через
`collMod`. Для всех трёх коллекций включены:

- `validationLevel: "strict"` — проверка каждого нового и изменяемого документа;
- `validationAction: "error"` — отклонение документа, который не соответствует схеме;
- `required` — обязательные поля;
- `bsonType` — типы BSON;
- `minLength`, `maxLength`, `minimum`, `maximum`, `enum`, `pattern` — ограничения значений;
- `additionalProperties: false` — запрет неизвестных полей верхнего уровня.

В `product_content.attributes` разрешены дополнительные характеристики простых типов. Это намеренная
гибкость документной модели, а не отключение валидации.

## 4. Бизнес-правила

| №   | Правило                                                                                                                             | Где обеспечивается                                    |
| --- | ----------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------- |
| 1   | ID товара и покупателя — положительные десятичные строки, соответствующие PostgreSQL BIGINT                                         | Прикладные проверки в `crud.js` и JSON Schema         |
| 2   | Оценка отзыва — целое число от 1 до 5; текст — от 3 до 3000 символов                                                                | `crud.js` и JSON Schema                               |
| 3   | Один покупатель может оставить только один отзыв на один товар                                                                      | Уникальный индекс MongoDB `{ productId, customerId }` |
| 4   | Нельзя изменить `productId`, `customerId` или `_id` существующего контент-документа/отзыва через предусмотренные функции обновления | Белый список обновляемых полей в `crud.js`            |
| 5   | Физическое удаление вопроса разрешено только в статусе `pending`                                                                    | Условие `deleteOne` в `crud.js`                       |

Валидатор MongoDB проверяет структуру и локальные значения одного документа. Он не заменяет
бизнес-проверки, которым нужны другие документы или PostgreSQL.

## 5. Установка и запуск

Требуются Docker Compose и Node.js 20 или новее.

Из корня репозитория:

```bash
# 1. Запустить MongoDB (отдельный compose, PostgreSQL не затрагивается)
docker compose -f mongodb/operations/docker-compose.yml up -d

# 2. Установить Node.js-зависимость
cd mongodb/operations
npm install

# 3. Проверить синтаксис файлов
npm run check

# 4. Создать коллекции и настроить валидацию
npm run validate

# 5. Выполнить демонстрацию CRUD и негативные проверки
npm run crud
```

По умолчанию используются `mongodb://127.0.0.1:27017` и база `online_store`. Их можно переопределить
переменными окружения `MONGODB_URI` и `MONGODB_DB`.

Остановить MongoDB:

```bash
docker compose -f mongodb/operations/docker-compose.yml down
```

Удалить также данные MongoDB:

```bash
docker compose -f mongodb/operations/docker-compose.yml down -v
```

## 6. Ожидаемые результаты

Успешный запуск `npm run validate` выводит сообщения `[OK]` о создании/обновлении трёх коллекций и
индексов.

Успешный запуск `npm run crud` демонстрирует:

- INSERT карточки товара, отзыва и вопроса;
- FIND карточки, отзывов и вопросов;
- UPDATE карточки товара и отзыва;
- DELETE ожидающего вопроса;
- отклонение документа без обязательного `title`;
- отклонение отзыва с рейтингом `6`;
- отклонение повторного отзыва по уникальному индексу;
- запрет удаления вопроса со статусом `answered`;
- запрет изменения идентификатора товара.

В конце демонстрации тестовые документы удаляются. Индексы и настройки валидации остаются в базе.

## 7. Контракт для участника №3

Чтобы дальнейшая разработка `mongodb/model/collections.js` не сломала CRUD участника №4, нужно
сохранить следующие договорённости:

1. Имена коллекций: `product_content`, `product_reviews`, `product_questions`.
2. Идентификаторы PostgreSQL в MongoDB: `productId` и `customerId` — строки с положительным
   десятичным числом.
3. `product_content` — один документ на один `productId`; `attributes`, `tags` и `gallery` остаются
   вложенными структурами.
4. `product_reviews` ссылается на товар и покупателя через `productId` и `customerId`; уникальность
   пары обеспечивается индексом.
5. `product_questions` ссылается на товар и покупателя; `answer` находится внутри вопроса.
6. Во всех документах присутствуют `schemaVersion: 1`, `createdAt` и `updatedAt`.
7. Валидация должна оставаться `strict` + `error`; если участник №3 меняет поля, он одновременно
   обновляет валидатор и CRUD, а не создаёт несовместимую схему.

Участник №3 может добавить собственный `collections.js` для описания модели и диаграмму, но не
должен повторно создавать эти коллекции с несовместимыми полями. Рекомендуется вынести общие
определения схемы в один модуль при интеграции.

## 8. Версионирование документов

Поле `schemaVersion` сейчас равно `1` и проверяется валидатором. При изменении структуры:

1. Согласовать новое поле/тип с владельцами модели и CRUD.
2. Подготовить миграцию старых документов (если требуется).
3. Обновить JSON Schema и код записи/чтения согласованно.
4. Переключить допустимую версию на `2` после миграции; не разрешать две версии случайно.
5. Проверить старые и новые документы отдельными позитивными и негативными тестами.

Для учебной версии валидатор намеренно принимает только `schemaVersion: 1`: это не даёт незаметно
записать документ неизвестной версии.
