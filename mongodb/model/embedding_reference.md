# Embedding и reference в модели MongoDB

## 1. Коллекции

| Коллекция           | Назначение                                     | Создаётся в                   |
| ------------------- | ---------------------------------------------- | ----------------------------- |
| `product_content`   | Карточка товара: характеристики, теги, галерея | `../operations/validation.js` |
| `product_reviews`   | Отзывы покупателей                             | `../operations/validation.js` |
| `product_questions` | Вопросы покупателей и ответы                   | `../operations/validation.js` |
| `product_showcases` | Подборки товаров (новинки, распродажа)         | `collections.js`              |

Базовые товары, покупатели, цены, остатки и заказы остаются в PostgreSQL.
MongoDB хранит только данные, у которых гибкая или растущая структура.

## 2. Связи

### 2.1. 1:N

Один товар имеет много отзывов и много вопросов. Связь хранится на стороне
«многих»: в каждом отзыве и вопросе лежит `productId`.

Индексы:

- `{ productId: 1, status: 1, createdAt: -1 }` для отзывов и вопросов;
- `{ productId: 1 }` уникальный для `product_content`.

### 2.2. M:N

Подборка содержит много товаров, а товар входит во много подборок. Связь
хранится массивом `productIds` в документе подборки.

Дополнительно M:N возникает между покупателями и товарами через
`product_reviews`: уникальный индекс `{ productId, customerId }` разрешает один
отзыв покупателя на один товар.

Запросы в обе стороны:

```javascript
db.product_showcases.aggregate([
	{ $match: { slug: 'demo-sale' } },
	{
		$lookup: {
			from: 'product_content',
			localField: 'productIds',
			foreignField: 'productId',
			as: 'products'
		}
	}
])

db.product_showcases.find({ productIds: '900001' })
```

Второй запрос использует мультиключевой индекс `showcases_by_product_id`.

## 3. Embedding

| Что встроено | Куда                | Чтение                                                                        | Обновление                                                 | Размер                                      |
| ------------ | ------------------- | ----------------------------------------------------------------------------- | ---------------------------------------------------------- | ------------------------------------------- |
| `attributes` | `product_content`   | Характеристики нужны всегда вместе с карточкой, отдельный запрос не требуется | Меняются редко, вместе с карточкой, одной операцией `$set` | Один плоский объект, значения простых типов |
| `tags`       | `product_content`   | Читаются вместе с карточкой                                                   | `$addToSet` и `$pull` без чтения документа                 | `maxItems: 30`, до 40 символов в теге       |
| `gallery`    | `product_content`   | Изображения нужны только при показе карточки                                  | Заменяются целиком                                         | `maxItems: 20`, URL до 2048 символов        |
| `answer`     | `product_questions` | Ответ читается вместе с вопросом                                              | Появляется один раз при ответе                             | До 4000 символов                            |

Критерий выбора embedding: данные принадлежат одному родителю, читаются вместе с
ним, не растут без ограничения и не нужны отдельно.

Разные категории имеют разные характеристики (одежда: `material`,
`sleeve_length`; обувь: `upper_material`, `sole_type`). В документной модели это
один объект `attributes` без отдельных таблиц и столбцов под каждый тип товара.

## 4. Reference

| Что вынесено                    | Куда ссылается                 | Почему не встроено                                                                                                                                                   |
| ------------------------------- | ------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Отзывы                          | `product_reviews.productId`    | Количество отзывов не ограничено, документ товара вырос бы до мегабайтов; отзывы модерируются и меняют статус независимо от товара; нужна выборка по рейтингу и дате |
| Вопросы                         | `product_questions.productId`  | Те же причины: рост без предела, независимый жизненный цикл, модерация                                                                                               |
| Товары подборки                 | `product_showcases.productIds` | Один товар входит в несколько подборок, копии документов товара дублировали бы данные                                                                                |
| Товар и покупатель в PostgreSQL | `productId`, `customerId`      | Источник истины находится в другой СУБД, копировать строки нельзя                                                                                                    |

Критерий выбора reference: данные растут, читаются и изменяются независимо от
родителя, либо принадлежат нескольким родителям.

## 5. Почему массив `productIds` лежит в подборке

Для M:N массив ссылок хранят на ограниченной стороне.

- Подборка курируется вручную, `maxItems: 200` ограничивает массив.
- Один товар может входить в произвольное число подборок, поэтому массив в
  `product_content` пришлось бы менять при каждом включении товара в подборку, а
  схема `product_content` согласована с CRUD и не изменяется.
- Запрос «товары подборки» читает один документ и выполняет `$lookup` по индексу
  `productId`.
- Запрос «подборки товара» использует мультиключевой индекс.

## 6. Размер документа

Лимит документа MongoDB — 16 МБ. Ограничения валидатора удерживают встроенные
структуры в безопасных пределах:

| Поле                           | Ограничение                    |
| ------------------------------ | ------------------------------ |
| `product_content.description`  | до 10000 символов              |
| `product_content.tags`         | до 30 элементов                |
| `product_content.gallery`      | до 20 элементов                |
| `product_showcases.productIds` | до 200 элементов, без повторов |
| `product_reviews.text`         | до 3000 символов               |
| `product_questions.answer`     | до 4000 символов               |

Документ `product_content` с максимальным заполнением занимает порядка 100 КБ,
документ подборки с 200 идентификаторами — несколько килобайт.

## 7. Сравнение embedding и reference на двух нагрузках

Сценарий: отзывы хранятся внутри документа товара (embedding) или в
`product_reviews` (reference).

| Нагрузка                                    | Embedding                                                                      | Reference                                                                        |
| ------------------------------------------- | ------------------------------------------------------------------------------ | -------------------------------------------------------------------------------- |
| A. Чтение карточки с 10 последними отзывами | Один `findOne` с проекцией `$slice`, но сервер читает весь документ с отзывами | Два запроса: карточка и выборка 10 отзывов по индексу `{ productId, createdAt }` |
| B. Добавление отзыва                        | `$push` в растущий документ, документ перезаписывается всё больше              | `insertOne` небольшого документа                                                 |

Скрипт `benchmark.js` создаёт отдельную базу `online_store_bench`, загружает по
умолчанию 100 товаров по 500 отзывов в оба варианта, выполняет обе нагрузки и
удаляет базу.

```bash
cd mongodb/model
mkdir -p results
npm run benchmark | tee results/benchmark.txt
```

Параметры задаются переменными окружения `BENCH_PRODUCTS`, `BENCH_REVIEWS`,
`BENCH_READS`, `BENCH_WRITES`.

Результаты замера (100 товаров по 500 отзывов, MongoDB в Docker на локальной
машине, файл `results/benchmark.txt`):

| Нагрузка                                    | Embedding                                | Reference |
| ------------------------------------------- | ---------------------------------------- | --------- |
| A. Чтение карточки с 10 последними отзывами | 1.095 мс                                 | 1.796 мс  |
| B. Добавление отзыва                        | 1.260 мс                                 | 0.789 мс  |
| Размер документа товара                     | 315 141 байт, после записей 327 756 байт | 347 байт  |

Выводы:

- На нагрузке A embedding быстрее примерно в 1.6 раза: нужен один запрос вместо
  двух. При локальном подключении сетевая задержка мала, поэтому выигрыш связан
  с числом запросов, а не с объёмом передаваемых данных.
- На нагрузке B reference быстрее примерно в 1.6 раза: вставка небольшого
  документа не зависит от числа существующих отзывов, а `$push` изменяет
  документ размером более 300 КБ.
- Документ с встроенными отзывами примерно в 900 раз больше документа карточки.
  При размере одного отзыва около 630 байт лимит документа в 16 МБ достигается
  примерно на 26 000 отзывах, а ограничить число отзывов без потери данных
  нельзя.
- Преимущество embedding на чтении сохраняется, пока массив небольшой. Для
  отзывов, число которых не ограничено и которые модерируются отдельно, выбран
  reference. Для `tags` и `gallery`, ограниченных валидатором, выбран embedding.

Итоговый вывод: небольшие ограниченные данные, читаемые вместе с родителем,
встраиваются; неограниченные и независимо изменяемые данные выносятся в
отдельную коллекцию.
