# Проверка после внесённых исправлений

## Что изменено

- Запрос 5 выбирает только продаваемые SKU с положительным остатком меньше 10.
- Генератор объясняет область воспроизводимости `setseed()`; размеры связанных таблиц рассчитываются от одного параметра `order_items_count`.
- Сценарии `transaction_commit.sql` и `transaction_rollback.sql` принимают `customer_email` через `psql -v`, а сценарий `order_lifecycle.sql` — email, артикул и количество.
- ROLLBACK моделирует бизнес-ошибку `PAYMENT_DECLINED`, после которой откатываются изменения заказа, корзины и остатков.
- `run_big.sh` теперь сохраняет результаты пяти бизнес-запросов на нагрузочном наборе до запуска бенчмарка.
- В отчёт добавлены примеры Q1 на 3 млн строк и подробный разбор плана Q2. Старые результаты Q5 намеренно не выдаются за актуальные: их нужно пересоздать после изменения запроса.

## Как проверить

1. Установить и запустить Docker Desktop.
2. Из корня проекта выполнить `bash run_all.sh`. Команда пересоздаёт тестовую базу и обновляет результаты малого набора.
3. Для нагрузочного набора выполнить `bash run_big.sh`. Команда пересоздаёт базу, генерирует 3 млн строк, обновляет `checks/results/business_queries_big.txt` и планы оптимизации. Это длительная операция.
4. Проверить `checks/results/verify.txt`, `checks/results/transaction_commit.txt`, `checks/results/transaction_rollback.txt`, `checks/results/business_queries.txt` и `checks/results/business_queries_big.txt`.
5. Для отдельной параметризованной транзакции можно выполнить из корня проекта: `docker compose exec -T db psql -U postgres -d online_store -v ON_ERROR_STOP=1 -v customer_email=anna@example.com -f /project/scenarios/transaction_commit.sql`. Указанный покупатель должен иметь активную корзину с доступными SKU.

## Ограничение проверки в текущем архиве

В среде подготовки архива не доступен Docker/клиент PostgreSQL, поэтому SQL-сценарии не были исполнены повторно после правок. Численные результаты и EXPLAIN-планы должны быть обновлены командами выше; существующие файлы результатов являются снимками прежних запусков и не заменяют повторный прогон.

## Дополнительные задания

В проекте остаются только два дополнительных пункта, которые уже были выполнены: сравнение `INSERT ... SELECT` и `COPY`, а также диагностика ожидания блокировки. Оценка влияния индекса на скорость вставки и объём хранилища не добавлялась, поскольку это было бы третьим дополнительным заданием.
