# Журнал архитектурных решений

## ADR-001. Разделение данных между PostgreSQL и MongoDB

**Проблема:** данные покупателей, заказов и каталога товаров имеют разную структуру и требования к хранению.

**Решение:**

- PostgreSQL используется для хранения покупателей, корзин и заказов.
- MongoDB используется для хранения категорий, товаров и SKU.

**Обоснование:** PostgreSQL подходит для связанных структурированных данных и транзакционных операций. MongoDB позволяет хранить документы с различающимися наборами характеристик.

## ADR-002. Хранение каталога в MongoDB

**Проблема:** товары разных категорий могут иметь различные характеристики.

**Решение:** весь каталог переносится в MongoDB и разделяется на три коллекции:

- `categories`;
- `products`;
- `skus`.

**Обоснование:** документная модель позволяет хранить характеристики товаров без создания отдельных таблиц или коллекций для каждого типа характеристик.

## ADR-003. Встраивание характеристик товаров

**Проблема:** характеристики относятся непосредственно к конкретному товару и могут отличаться в зависимости от его категории.

**Решение:** хранить характеристики внутри документа `products` в объекте `attributes`.

**Обоснование:** embedding позволяет получать основную информацию о товаре и его характеристики из одного документа.

## ADR-004. Отдельная коллекция для SKU

**Проблема:** один товар может иметь несколько вариантов с разными ценами, остатками, размерами и цветами.

**Решение:** хранить каждый вариант в отдельном документе коллекции `skus`. Для связи с товаром использовать поле `product_id`.

**Обоснование:** отдельное хранение позволяет изменять цену и остаток конкретного варианта без изменения документа товара.

## ADR-005. Использование UUID

**Проблема:** после переноса каталога в MongoDB необходимо сохранить возможность связывать SKU с позициями корзин и заказов в PostgreSQL.

**Решение:** использовать UUID в качестве идентификаторов документов MongoDB и хранить соответствующие UUID в полях `cart_items.sku_id` и `order_items.sku_id` PostgreSQL.

**Обоснование:** единый формат идентификаторов упрощает создание логических связей между двумя СУБД.

**Ограничение:** обычные внешние ключи между PostgreSQL и MongoDB отсутствуют.

## ADR-006. Разделение актуальной и исторической цены

**Проблема:** цена товара может изменяться после оформления заказа.

**Решение:**
- Актуальная цена хранится в `skus.price` MongoDB.
- Цена на момент покупки сохраняется в `order_items.fixed_price` PostgreSQL.

**Обоснование:** изменение цены в каталоге не должно изменять стоимость ранее оформленного заказа.

## ADR-007. Отсутствие общей транзакции между СУБД

**Проблема:** PostgreSQL и MongoDB являются независимыми системами хранения и не обеспечивают общую ACID-транзакцию.

**Решение:** транзакции выполняются отдельно в каждой СУБД. Межбазовые операции не рассматриваются как единая атомарная транзакция.

**Последствие:** изменение данных в одной базе не гарантирует автоматического изменения связанных данных в другой.

## ADR-008. Сохранение SKU, используемых в заказах

**Проблема:** физическое удаление SKU может нарушить связь с историческими позициями заказов.

**Решение:** вместо физического удаления таких SKU используется изменение поля `status` на неактивное значение.

**Обоснование:** это позволяет сохранять ссылки из заказов на соответствующие варианты товаров.

## ADR-009. Изменение структуры документов

**Проблема:** при развитии каталога может потребоваться добавление, удаление или изменение полей документов.

**Решение:**
- Новые необязательные поля допускается добавлять без обязательного изменения всех существующих документов.
- При добавлении обязательных полей обновляются существующие документы.
- При изменении типов или названий полей выполняется преобразование существующих документов.
- После изменения структуры корректируются правила валидации.

Отдельное версионирование каждого документа не используется.

**Обоснование:** для текущей структуры достаточно контролировать изменения схемы коллекций и обновлять существующие данные при необходимости.
