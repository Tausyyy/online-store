# Распределение данных и владение ими

## 1. Назначение документа

Документ определяет целевое распределение данных предметной области
интернет-магазина между PostgreSQL и MongoDB.

Описанная архитектура является проектируемой моделью хранения данных,
на основании которой должна быть переработана существующая реализация
лабораторной работы.

Основной принцип распределения: каждый тип данных имеет одну СУБД,
являющуюся его источником истины. Это позволяет избежать необоснованного
дублирования актуальных данных и определить ответственность каждой
системы хранения.

## 2. Общая модель владения данными

В проектируемой архитектуре обязанности распределяются следующим образом:

- **PostgreSQL** — покупатели, корзины и заказы. СУБД используется
  для хранения структурированных данных с реляционными связями.
- **MongoDB** — каталог товаров: категории, товары, характеристики
  и варианты SKU. СУБД используется для хранения документов с гибкой
  структурой и вложенными данными.

Таким образом, PostgreSQL отвечает за данные коммерческих операций,
а MongoDB — за данные каталога.

## 3. Данные PostgreSQL

В PostgreSQL предполагается хранить следующие сущности:

| Таблица | Содержание | Источник истины |
|---|---|---|
| `customers` | Данные покупателей и контактная информация | PostgreSQL |
| `carts` | Корзины покупателей и их состояние | PostgreSQL |
| `cart_items` | Состав корзин: идентификатор SKU и количество | PostgreSQL |
| `orders` | Заказы, покупатель, параметры доставки и оплаты, состояние заказа | PostgreSQL |
| `order_items` | Позиции заказа, выбранный SKU, количество и зафиксированная цена | PostgreSQL |

PostgreSQL является единственным источником истины для перечисленных
сущностей.

Таблицы `cart_items` и `order_items` содержат идентификатор SKU,
который соответствует документу в MongoDB. При этом полная информация
о товаре и его варианте в PostgreSQL не дублируется.

### 3.1. Особенность хранения цены заказа

Поле `order_items.fixed_price` хранит цену SKU на момент оформления
заказа.

Это исторический снимок, необходимый для сохранения информации
о совершённой покупке.

Изменение актуальной цены SKU в MongoDB не должно изменять стоимость,
зафиксированную в ранее созданном заказе.

Следовательно, `fixed_price` не является альтернативным источником
актуальной цены товара.

## 4. Данные MongoDB

Для хранения каталога в MongoDB предусматриваются три коллекции:

| Коллекция | Содержание | Источник истины |
|---|---|---|
| `categories` | Категории каталога и их описания | MongoDB |
| `products` | Основные сведения о товарах и их характеристики | MongoDB |
| `skus` | Варианты товаров, артикулы, цены и остатки | MongoDB |

### 4.1. Коллекция categories

Коллекция `categories` предназначена для хранения категорий товаров.

Каждая категория представляет собой отдельный документ.
Для связи с товарами используется идентификатор категории,
на который ссылается поле `category_id` в коллекции `products`.

Выделение категорий в отдельную коллекцию позволяет использовать
одну категорию для множества товаров без повторного хранения
её полного описания в каждом документе.

### 4.2. Коллекция products

Коллекция `products` содержит общую информацию о товарах:

- название;
- описание;
- бренд;
- идентификатор категории;
- статус публикации;
- характеристики товара.

Характеристики хранятся непосредственно внутри документа
в объекте `attributes`.

Примеры характеристик:

- одежда: материал, длина рукава, тип воротника;
- обувь: материал верха, тип подошвы;
- аксессуары: материал изготовления, тип застёжки.

Набор характеристик может различаться в зависимости от типа товара.
Поэтому документная модель позволяет хранить их без создания
отдельных таблиц для каждого типа характеристик.

### 4.3. Коллекция skus

Коллекция `skus` предназначена для хранения отдельных вариантов товаров.

Каждый документ SKU содержит:

- `product_id` — идентификатор родительского товара;
- `sku_code` — артикул;
- `size` — размер, если применимо;
- `color` — цвет, если применимо;
- `price` — актуальную цену;
- `stock` — количество на складе;
- `status` — состояние варианта.

Связь между `products` и `skus` имеет тип 1:N:
одному товару может соответствовать несколько вариантов SKU,
при этом каждый SKU относится к одному товару.

SKU выделены в отдельную коллекцию, поскольку варианты могут
независимо изменять цену, остаток и статус.

Такое решение позволяет обращаться к отдельным вариантам
без необходимости загружать и изменять весь документ товара.

## 5. Источники истины по типам данных

| Тип данных | Источник истины | Особенности |
|---|---|---|
| Покупатели | PostgreSQL | Не дублируются в MongoDB |
| Корзины | PostgreSQL | Состав хранится отдельно |
| Позиции корзин | PostgreSQL | Содержат ссылку на SKU |
| Заказы | PostgreSQL | Хранят информацию о покупке |
| Позиции заказов | PostgreSQL | Содержат ссылку на SKU и историческую цену |
| Категории | MongoDB | Отдельные документы |
| Основная информация о товарах | MongoDB | Хранится в products |
| Характеристики товаров | MongoDB | Вложенный объект attributes |
| Варианты SKU | MongoDB | Отдельная коллекция |
| Артикулы | MongoDB | Поле sku_code |
| Актуальные цены | MongoDB | Поле price в документе SKU |
| Остатки товаров | MongoDB | Поле stock в документе SKU |

## 6. Идентификаторы и связи между СУБД

Для документов коллекций `categories`, `products` и `skus`
предусматривается использование UUID в качестве идентификатора
в поле `_id`.

Внутренние связи MongoDB:

- `products.category_id` ссылается на `categories._id`;
- `skus.product_id` ссылается на `products._id`.

Для связи PostgreSQL с MongoDB используются идентификаторы SKU:

- `cart_items.sku_id` содержит UUID документа из `skus`;
- `order_items.sku_id` содержит UUID документа из `skus`.

Эти связи являются логическими, поскольку PostgreSQL и MongoDB
представляют собой независимые системы хранения данных.

Обычные ограничения FOREIGN KEY между разными СУБД
в данной архитектуре не применяются.

При этом идентификаторы должны оставаться неизменными
на протяжении жизненного цикла соответствующих документов.

Изменение названия, цены, характеристик или статуса
не должно приводить к изменению идентификатора.

## 7. Обоснование распределения данных

### 7.1. Почему каталог хранится в MongoDB

Каталог содержит товары с различающимися наборами характеристик.

В реляционной модели для этого могут потребоваться дополнительные
таблицы, большое количество необязательных столбцов или сложные
связи между сущностями.

MongoDB позволяет хранить характеристики непосредственно
в документе товара в виде вложенного объекта `attributes`.

При этом SKU выделены отдельно, поскольку представляют собой
самостоятельные варианты товара с собственными ценами,
остатками и статусами.

### 7.2. Почему покупатели, корзины и заказы хранятся в PostgreSQL

Эти данные имеют чёткую реляционную структуру.

Между покупателями, корзинами, позициями корзин, заказами
и позициями заказов существуют зависимости, для которых важны
внешние ключи, ограничения целостности и транзакции.

PostgreSQL подходит для хранения таких данных благодаря
поддержке реляционной модели и ACID-транзакций.

## 8. Ограничения и правила согласованности

1. Каждый тип актуальных данных должен иметь только один
   источник истины.

2. Актуальная цена и остаток SKU определяются исключительно
   документом соответствующего варианта в MongoDB.

3. Значение `order_items.fixed_price` является исторической
   информацией и не заменяет актуальную цену из MongoDB.

4. PostgreSQL не обеспечивает обычную ссылочную целостность
   для идентификаторов документов MongoDB.

5. Существование SKU, на который ссылаются записи PostgreSQL, не контролируется ограничениями внешнего ключа. 
   Проверка таких логических связей должна выполняться отдельно при операциях работы с данными.

6. MongoDB поддерживает атомарность операций над отдельным
   документом. Это позволяет выполнять изменение остатка
   конкретного SKU с проверкой его текущего значения.

7. PostgreSQL и MongoDB не поддерживают общую ACID-транзакцию
   между собой. Поэтому операции, затрагивающие обе СУБД,
   требуют отдельного рассмотрения согласованности данных.

8. Удаление SKU должно учитывать существующие ссылки
   из корзин и заказов. Исторические сведения о завершённых
   заказах должны сохраняться.
