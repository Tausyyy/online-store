# Интеграция PostgreSQL и MongoDB

## 1. Назначение

В проекте используются PostgreSQL и MongoDB. Каждая база отвечает за свою часть данных.

PostgreSQL хранит покупателей, корзины и заказы. MongoDB хранит каталог товаров: категории, товары, характеристики и варианты SKU.

## 2. Какие данные передаются между базами

Для связи между базами используется идентификатор SKU.

В MongoDB у каждого документа SKU есть UUID. Этот идентификатор сохраняется в PostgreSQL в позициях корзины и заказа.

Связь между базами логическая: PostgreSQL не может создать обычный внешний ключ на документ MongoDB.

## 3. Оформление заказа

Предполагается следующий порядок действий:

1. Покупатель выбирает товар и его вариант в каталоге.
2. Приложение получает из MongoDB данные SKU: идентификатор, актуальную цену и доступный остаток.
3. Приложение проверяет наличие нужного количества товара.
4. В PostgreSQL создаются заказ и его позиции.
5. В `order_items` сохраняются идентификатор SKU, количество и цена на момент покупки (`fixed_price`).

Цена в `fixed_price` нужна для истории заказа. Если актуальная цена товара позже изменится в MongoDB, стоимость уже оформленного заказа останется прежней.

## 4. Как избежать дублирования данных

Актуальные данные каталога хранятся в MongoDB. Не нужно создавать в PostgreSQL вторую копию всего каталога.

В PostgreSQL сохраняются только данные, необходимые для коммерческих операций:
- идентификатор SKU;
- количество;
- цена на момент покупки.

Если для отчётов нужны название товара и категория на момент покупки, их можно сохранять как снимок в позиции заказа. Такой снимок не заменяет актуальные данные каталога и нужен для сохранения истории.

## 5. Работа аналитических запросов

В текущем наборе SQL-запросов №2, №3 и №8 используются таблицы `categories`, `products` и `sku`.

В целевой архитектуре каталог находится в MongoDB, поэтому эти запросы нельзя оставить без изменений: обычный SQL JOIN между таблицами PostgreSQL и коллекциями MongoDB не выполняется.

Перед переносом каталога нужно выбрать способ подготовки данных для аналитики. Один из простых вариантов — сохранять в PostgreSQL в позиции заказа снимок необходимых сведений о товаре: идентификатор товара, название и категорию. После этого аналитические запросы можно будет строить по данным заказов и их снимкам.

Запросы №1, №4, №5, №6 и №7 используют только покупателей, заказы и позиции заказов. Их логика не зависит от таблиц каталога.

## 6. Ограничения согласованности

PostgreSQL и MongoDB не используют общую транзакцию. Поэтому операции, затрагивающие обе базы, нужно выполнять с учётом возможной ошибки на одном из этапов.

Например, если проверка SKU в MongoDB прошла, но создание заказа в PostgreSQL завершилось ошибкой, заказ не должен считаться оформленным.

Также при удалении SKU нужно учитывать ссылки на него в корзинах и заказах. Исторические данные завершённых заказов должны сохраняться.

## 7. Что нужно учесть при переходе к целевой архитектуре

В текущей SQL-схеме `cart_items.sku_id` и `order_items.sku_id` имеют тип `BIGINT` и ссылаются внешним ключом на таблицу `sku`.

В целевой архитектуре `sku_id` должен хранить UUID документа MongoDB, а межбазовая связь будет логической.

Поэтому перед переходом необходимо:
1. Согласовать тип UUID для `sku_id`.
2. Убрать внешний ключ на локальную таблицу `sku`.
3. Определить, какие сведения о товаре сохраняются в позиции заказа для истории и аналитики.
4. Изменить запросы №2, №3 и №8 с учётом выбранного способа подготовки аналитических данных.

До согласования этих изменений существующую SQL-схему и запросы менять не нужно.

## 8. Вывод

MongoDB является источником истины для каталога, а PostgreSQL — для покупателей, корзин и заказов.

Связь между базами выполняется через UUID SKU. Цена в заказе сохраняется отдельно, чтобы история покупок не зависела от изменения каталога.

Для аналитики необходимо отдельно предусмотреть сведения о товарах и категориях, так как SQL-запросы PostgreSQL не могут напрямую объединять таблицы с коллекциями MongoDB.
