# Интеграция PostgreSQL и MongoDB

## 1. Назначение

В проекте используются две СУБД. PostgreSQL хранит покупателей, корзины и заказы. MongoDB предназначена для хранения каталога: категорий, товаров и вариантов SKU.

Описанная ниже схема является целевой. Сейчас каталог ещё присутствует в SQL-схеме PostgreSQL, поэтому перенос и настройка интеграции не считаются завершёнными.

## 2. Связь между базами

Для связи используется идентификатор SKU.

В целевой модели документ SKU в MongoDB получает UUID. Этот UUID должен храниться в PostgreSQL в полях `cart_items.sku_id` и `order_items.sku_id`.

Это логическая связь: обычный внешний ключ PostgreSQL не может ссылаться на документ MongoDB.

## 3. Оформление заказа

Предполагаемый порядок оформления заказа:

1. Приложение получает из MongoDB выбранный SKU, его актуальную цену и остаток.
2. Приложение проверяет, достаточно ли товара.
3. В PostgreSQL создаются заказ и его позиции.
4. В `order_items` сохраняются UUID SKU, количество и цена на момент покупки (`fixed_price`).

`fixed_price` нужен для истории заказа. Если актуальная цена в MongoDB изменится, стоимость уже оформленного заказа останется прежней.

## 4. Дублирование данных

Актуальные сведения о товарах, категориях, ценах и остатках должны храниться в MongoDB.

В PostgreSQL не требуется хранить вторую копию всего актуального каталога. Там остаются данные, необходимые для оформления и хранения заказов.

Для истории заказа можно сохранять снимок названия товара и категории на момент покупки. Такой снимок не является источником актуальных сведений о каталоге.

## 5. Аналитические запросы

Сейчас запросы №2, №3 и №8 используют таблицы `categories`, `products` и `sku` в PostgreSQL. В целевой архитектуре каталог должен находиться в MongoDB, поэтому эти запросы после переноса каталога не смогут работать без изменений.

Запросы №1, №4, №5, №6 и №7 используют покупателей, заказы и позиции заказов и не обращаются к таблицам каталога.

Для сохранения аналитики нужно отдельно согласовать, какие сведения о товаре будут сохраняться в PostgreSQL вместе с позицией заказа. Возможный вариант — хранить в `order_items` снимок названия товара и категории на момент покупки. После этого запросы по продажам товаров и категорий можно будет переписать с использованием данных PostgreSQL.

Этот вариант пока является предложением. Он требует согласования с участниками, отвечающими за SQL и MongoDB, и не считается реализованным.

## 6. Что потребуется изменить при переходе

В текущей SQL-схеме `cart_items.sku_id` и `order_items.sku_id` имеют тип `BIGINT` и ссылаются внешним ключом на таблицу `sku`.

В целевой архитектуре эти поля должны хранить UUID документов MongoDB. Для перехода потребуется:

1. Согласовать формат UUID для идентификаторов SKU.
2. Изменить тип полей `cart_items.sku_id` и `order_items.sku_id`.
3. Удалить внешние ключи на локальную таблицу `sku`.
4. Определить, какие сведения о товаре сохраняются в позиции заказа для истории и аналитики.
5. Согласовать изменения аналитических запросов №2, №3 и №8.

До согласования этих изменений текущую SQL-схему и запросы менять не нужно.

## 7. Ограничения

PostgreSQL и MongoDB не используют общую ACID-транзакцию. Поэтому приложение должно учитывать ситуацию, когда операция в одной базе прошла, а операция во второй завершилась ошибкой.

При удалении SKU нужно учитывать ссылки из корзин и заказов. Для SKU, которые уже использовались в заказах, архитектура предусматривает перевод в неактивный статус вместо физического удаления.

## 8. Вывод

В целевой архитектуре MongoDB является источником истины для каталога, а PostgreSQL — для покупателей, корзин и заказов.

Связь между базами выполняется через UUID SKU. Цена в заказе сохраняется отдельно как историческое значение.

Перенос каталога, изменение типов идентификаторов и подготовка данных для аналитики являются дальнейшими задачами реализации. На момент подготовки документа эти изменения ещё не выполнены.
