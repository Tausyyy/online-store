# Приведение модели к третьей нормальной форме (3НФ)

Разработанная реляционная модель базы данных интернет-магазина одежды
приведена к третьей нормальной форме.

Цель нормализации --- устранение избыточности данных, предотвращение
аномалий вставки, удаления и обновления, а также обеспечение целостности
информации.

------------------------------------------------------------------------

## Первая нормальная форма (1НФ)

Модель соответствует требованиям первой нормальной формы, так как:

-   все атрибуты таблиц содержат атомарные значения;
-   отсутствуют группы повторяющихся данных;
-   каждая запись однозначно идентифицируется первичным ключом.

Например, характеристики товара (размер и цвет) не хранятся в одном поле
в виде списка.

Вместо этого используется отдельная сущность SKU, где каждый вариант
товара представлен отдельной записью.

Пример:

Товар:

    Футболка Basic

Варианты:

    Чёрный, размер M
    Белый, размер L

хранятся отдельными строками в таблице SKU.

------------------------------------------------------------------------

## Вторая нормальная форма (2НФ)

Модель соответствует требованиям второй нормальной формы, так как все
неключевые атрибуты полностью зависят от первичного ключа своей таблицы.

Были разделены сущности, имеющие собственные наборы атрибутов.

Таблица products содержит общую информацию о товаре:

    product_id
    name
    description
    brand

Таблица sku содержит характеристики конкретного варианта товара:

    sku_id
    product_id
    size
    color
    price
    stock_quantity

Таким образом, информация о товаре и информация о его вариантах не
смешиваются в одной таблице.

------------------------------------------------------------------------

## Третья нормальная форма (3НФ)

Модель соответствует третьей нормальной форме, так как все неключевые
атрибуты зависят только от первичного ключа своей таблицы и отсутствуют
транзитивные зависимости.

### Выделение категорий товаров

Категория вынесена в отдельную таблицу categories.

До нормализации данные могли бы храниться так:

    products

    product_id
    product_name
    category_name
    category_description

Такая структура приводит к повторению информации о категории для каждого
товара.

После нормализации:

    categories

    category_id
    name
    description


    products

    product_id
    category_id
    name
    description
    brand

Информация о категории хранится только в одном месте.

------------------------------------------------------------------------

### Разделение товара и его вариантов

Товар и варианты товара разделены на две сущности:

    products

и

    sku

Один товар может иметь несколько вариантов, отличающихся размером,
цветом, ценой и остатком.

Например:

    Футболка Basic
        |
        ├── Чёрная M
        ├── Чёрная L
        └── Белая M

Хранение таких данных в одной таблице привело бы к повторению информации
о товаре.

------------------------------------------------------------------------

### Разделение заказа и состава заказа

Заказ и позиции заказа вынесены в разные таблицы:

    orders

и

    order_items

Таблица orders хранит информацию о самом заказе:

-   покупатель;
-   статус;
-   дата создания;
-   способ получения;
-   способ оплаты.

Таблица order_items хранит:

-   выбранный SKU;
-   количество;
-   зафиксированную цену.

Это позволяет одному заказу содержать любое количество товаров без
создания дополнительных полей.

------------------------------------------------------------------------

# Намеренная денормализация

В текущей модели намеренная денормализация не применяется.

Модель сохраняется в нормализованном виде, так как:

-   проект имеет учебный масштаб;
-   объём данных не требует оптимизации за счёт дублирования;
-   приоритетом является сохранение целостности данных;
-   уменьшение количества дублирующей информации упрощает сопровождение
    базы.

------------------------------------------------------------------------

## Возможный вариант денормализации

Одним из вариантов намеренной денормализации могло бы быть добавление
названия товара непосредственно в таблицу order_items.

Например:

    order_items

    order_item_id
    order_id
    sku_id
    product_name
    quantity
    fixed_price

Преимущество:

-   при просмотре истории заказов не требуется дополнительное соединение
    с таблицами SKU и товара.

Однако такой подход приводит к дублированию данных.

Название товара будет храниться одновременно:

    products.name

и

    order_items.product_name

При изменении названия товара потребуется синхронизация нескольких мест
хранения данных.

Поэтому в рамках проекта принято решение отказаться от такой
денормализации и оставить нормализованную структуру.

------------------------------------------------------------------------

# Итог

Разработанная модель соответствует третьей нормальной форме.

Разделение сущностей на отдельные таблицы позволяет:

-   избежать дублирования информации;
-   обеспечить ссылочную целостность через внешние ключи;
-   упростить изменение и сопровождение базы данных;
-   сохранить корректность данных при изменении отдельных сущностей.

# Архитектура проекта и интеграция PostgreSQL и MongoDB

## 1. Общая архитектура

В проекте Online Store используются две системы управления базами данных: PostgreSQL и MongoDB.

Каждая СУБД отвечает за собственную область данных.

PostgreSQL используется для хранения основных структурированных данных интернет-магазина, MongoDB — для хранения дополнительной информации о товарах и взаимодействии покупателей с ними.

## 2. Распределение данных

### PostgreSQL

В PostgreSQL хранятся:

- Покупатели (`customers`);
- Категории товаров (`categories`);
- Товары (`products`);
- Варианты товаров (`sku`);
- Корзины (`carts`);
- Заказы (`orders`);
- Позиции заказов (`order_items`).

PostgreSQL является источником истины для перечисленных сущностей.

### MongoDB

В MongoDB используются следующие коллекции:

- `product_content` — дополнительная информация о товарах;
- `product_reviews` — отзывы покупателей;
- `product_questions` — вопросы и ответы;
- `product_showcases` — подборки товаров.

MongoDB отвечает за дополнительный контент, который не требуется включать в основную реляционную модель.

## 3. Взаимодействие между СУБД

Связь между PostgreSQL и MongoDB осуществляется через идентификаторы товаров.

Например, документ отзыва в MongoDB содержит идентификатор товара, к которому относится отзыв.

При этом основные сведения о товаре хранятся в PostgreSQL.

Такой подход позволяет избежать необоснованного дублирования информации и разделить ответственность между базами данных.

## 4. Сравнение JSONB в PostgreSQL и MongoDB

Рассмотрим сценарий хранения дополнительного контента карточки товара.

### Вариант 1. PostgreSQL JSONB

Дополнительные характеристики товара можно хранить в поле JSONB таблицы `products`.

**Преимущества:**

- Данные находятся в одной базе;
- Не требуется отдельное обращение к MongoDB;
- Поддерживаются индексация и запросы по JSON-полям;
- Сохраняется связь с реляционной моделью.

**Недостатки:**

- Дополнительные данные находятся внутри реляционной записи;
- Сложнее независимо управлять большим количеством вложенных структур;
- Изменение структуры может усложнять сопровождение при большом разнообразии документов.

### Вариант 2. MongoDB

Дополнительный контент хранится в отдельной коллекции `product_content`.

**Преимущества:**

- Гибкая структура документов;
- Возможность использовать вложенные объекты и массивы;
- Независимое обновление дополнительного контента;
- Удобство работы с документами различной структуры.

**Недостатки:**

- Появляется необходимость взаимодействия двух СУБД;
- Отсутствуют общие внешние ключи между PostgreSQL и MongoDB;
- Необходимо контролировать согласованность идентификаторов.

### Вывод

Для небольших динамических характеристик, тесно связанных с товаром, подходит JSONB.

Для дополнительного контента с самостоятельной структурой и отдельными операциями чтения и обновления удобнее использовать MongoDB.

В рамках проекта выбран второй вариант.

## 5. Проверка отсутствия дублирования

В проекте используется разделение ответственности:

- PostgreSQL хранит основные сведения о товарах и заказах;
- MongoDB хранит дополнительный контент, отзывы, вопросы и подборки;
- Идентификаторы товаров используются для связи данных.

Таким образом, две СУБД не являются независимыми копиями одной базы данных.

## 6. Итог интеграции

Использование PostgreSQL и MongoDB позволяет объединить преимущества реляционной и документной моделей.

PostgreSQL обеспечивает структурированность, транзакционность и целостность основных бизнес-данных.

MongoDB обеспечивает гибкость хранения дополнительной информации.

Выбранная архитектура соответствует разделению данных по назначению и позволяет расширять функциональность интернет-магазина без необоснованного усложнения реляционной модели.
